## Axis Research

### Axis 1 — Architecture: multi-process state in a FastAPI/uvicorn app (medium+/high)

#### CANONICAL — what `--workers` actually means

- **`--workers N` spawns N independent OS processes with no shared memory; each has its own event loop and its own module-level state.** Source: uvicorn settings docs <https://uvicorn.dev/settings/>; uvicorn deployment docs <https://uvicorn.dev/deployment/>.
  *Why it matters here:* every one of the ~20 in-process holders in the confirmed problem (rate-limit buckets, `_GITHUB_STATES`, index single-flight, mint/provision/invite locks, `_dream_lock`, capture admission) exists **N times, independently**, and each copy will happily issue its own decision.
- **`--workers` defaults to `$WEB_CONCURRENCY` when set, otherwise `1`; `--workers` is invalid with `--reload`.** Source: <https://uvicorn.dev/settings/>; Ubuntu uvicorn(1) manpage <https://manpages.ubuntu.com/manpages/noble/man1/uvicorn.1.html>.
  *Why it matters here:* the repo's `Dockerfile.hosted` CMD passes **no** `--workers` and no `WEB_CONCURRENCY` → effective workers = 1 today, and the count is env-overridable by anything that can set a Fly env var. The "worker count stays at 1" deliverable is one env var away from being false.
- **Uvicorn standalone does NOT fork — it uses `multiprocessing.get_context("spawn")`.** Verified in source: `uvicorn/_subprocess.py` — `spawn = multiprocessing.get_context("spawn")`, `get_subprocess()` builds a `SpawnProcess(**kwargs)`. Source: <https://github.com/encode/uvicorn/blob/master/uvicorn/_subprocess.py>.
  *Why it matters here:* **this contradicts the issue's own P1-2 wording, "uvicorn forks with identical env"** (see *Findings that contradict*). Under `spawn`, each worker is a **fresh interpreter that re-imports the app** — module-level state is not copy-on-write shared, it is *re-executed*, and every import-time side effect (including the ~85s torch/model pre-warm) runs N times in full.
- **The listening socket is bound ONCE in the parent and passed to the children.** Same source, docstring: *"Sockets are bound once by the parent process, and then passed to the child processes."*
  *Why it matters here:* the uvicorn port 8000 needs no change at workers=2 — but this is exactly why the app's **own** 9090 listener is a different problem (it is opened by the app, per process).
- **No per-worker identifier is passed to the worker — not by env, not by argv.** Uvicorn's `--workers` is a *count* setting only; `subprocess_started()` mutates nothing but `sys.stdin` and logging (source read above). The docs and manpage document no worker-ID mechanism. The child *does* receive the pickled `Config` object, but that exposes `Config.workers` (a count), not an index, and no reference to it reaches the ASGI app.
  *Why it matters here:* this is the canonical confirmation of the issue's conclusion that `TORTOISE_DAEMON_WORKER`-style env designation is not implementable — and it means worker roles must be **self-elected at runtime** (lock/port), never assigned by config.
- **Fail-closed in the supervisor: a worker that exits with `STARTUP_FAILURE` stops the whole parent.** Verified: `uvicorn/supervisors/multiprocess.py::keep_subprocess_alive` → `if process.exitcode == STARTUP_FAILURE: … self.should_exit.set()`, and `run()` then calls `terminate_all()`. Source: <https://github.com/encode/uvicorn/blob/master/uvicorn/supervisors/multiprocess.py>.
  *Why it matters here:* **any unhandled exception in the startup half of `_lifespan` on ONE worker takes down the machine**, i.e. a per-worker boot step that fails only on worker ≥2 is a container crash-loop, not a warning. ⚠️ Version caveat: verified at `master`; the repo pins `uvicorn>=0.23.0` — re-verify the `STARTUP_FAILURE`-aborts-parent path at the lock-resolved version before relying on it.

#### CANONICAL — sharing state across workers, and leader election on one machine

- **The convergent answer for cross-worker state is an external store, not in-process memory: session/CSRF/rate-limit state goes to Redis (or the DB), with TTLs and single-use deletion.** Sources: fastapi-practices `fastapi_best_architecture` OAuth2 CSRF pattern — `state` token written to Redis with a TTL and deleted on callback validation <https://deepwiki.com/fastapi-practices/fastapi_best_architecture/6.5-oauth2-social-login>; IBM `mcp-context-forge` OAuth troubleshooting — "in-memory storage does not share state across workers; use `CACHE_TYPE=database` or `CACHE_TYPE=redis`" <https://ibm.github.io/mcp-context-forge/latest/manage/oauth-troubleshooting/>. Both are *single-implementation* precedents (⚠️ two sources, same pattern class).
  *Why it matters here:* `_GITHUB_STATES` is the launch-critical instance — the issue's P1-C says onboarding would intermittently CSRF-400. The field's fix is unambiguous: that state must leave the worker process. Note the `state`-token case is *not* merely "share it" — it is share-with-TTL-and-single-use, which is a stronger contract than a shared dict.
- **Sticky sessions are the alternative and they are worse for this app.** IBM's config notes Redis is required for session affinity in multi-worker deployments (source above). *Why it matters here:* Fly Proxy host-balances across workers with no affinity guarantee, so sticky-session routing would need Fly-level work — and would still leave rate-limit buckets N× wrong.
- **On a single machine, the canonical leader-election primitives are `flock`/`fcntl`, a lock row, or Redis `SET NX PX`. Their failure modes differ sharply:**
  - **`flock` is tainted by *any* file-descriptor close on the same open file description, and is not reliably implemented on NFS/CIFS.** Sources: Python `fcntl` library notes — closing a file descriptor referring to the file can release that process's locks, and `flock` has portability pitfalls <https://docs.python.org/3/library/fcntl.html>; runebook `fcntl` reference (same caveat, more explicit) <https://runebook.dev/en/docs/python/library/fcntl>; `flock(1)` man page — NFS and CIFS have limited `flock(2)` implementations that may fail depending on mount options <https://www.mankier.com/1/flock>.
  - **`flock` is crash-safe without a lease:** the lock is released by the kernel when the holder exits, *including on SIGKILL*. Source: cron-patterns design note <https://archon-eight.vercel.app/devops/cron-patterns>. Redis locks, by contrast, **require a TTL** or a crashed holder blocks progress forever; delete-if-still-holder (fencing token) is needed to avoid releasing another client's lock. Sources: same note; <https://scalablesystem.dev/system-design/build-a-distributed-lock-manager-and-leader-election-service>; `SET key value NX PX timeout` pattern <https://credmark.ai/practice/top-distributed-backend-interview-questions-and-answers>.
  - *Why it matters here:* `tortoise/shared_state/concurrency.py::flock_exclusive` is a **sound choice for single-machine leader election** — it opens its own fd per call and closes it at exit, and crash-safety needs no TTL. The two caveats are specific and actionable: (1) any *other* code that opens-and-closes that same lock-file path can silently drop the lock; (2) the same process opening the path twice gets **two independent lock descriptions**, so a re-entrant acquire in one worker returns `BlockingIOError` and surfaces as the existing `TimeoutError` after `timeout_ms` — not as a nested lock. Fly volumes are host-local block storage, so the NFS/CIFS caveat does **not** apply here (it would apply to a shared/network filesystem).

#### COMPETITOR-PRECEDENT — running periodic work and boot-once work without N executions

- **The field converges on: do not run periodic work inside the request-serving workers.** Documented options, in descending order of how often they are recommended:
  - **A dedicated process / separate process group** — APScheduler discussion 1088: with Gunicorn workers each gets its own scheduler so jobs run N times; remedy is *a separate scheduler process* or shared datastore + leader election <https://github.com/agronholm/apscheduler/discussions/1088>; Sanic #1011 says the same <https://github.com/sanic-org/sanic/issues/1011>; `celery beat` is *single-process by design* and multiple beat instances duplicate every scheduled execution <https://www.edgeservers.com.au/en/articles/python-celery-redis-workers>.
  - **A platform scheduler (Kubernetes CronJob, Fly process group) when the work is self-contained** — same Celery source; <https://async-concurrency.com/concurrent-execution-worker-patterns/background-jobs-and-task-queues/> recommends a platform CronJob for self-contained work.
  - **A shared job store + per-slot lock** for exact-once-per-slot semantics across replicas — <https://async-concurrency.com/concurrent-execution-worker-patterns/background-jobs-and-task-queues/scheduling-cron-jobs-inside-an-asyncio-service/> (lock keyed by *job and slot*, plus an explicit skip-vs-replay policy for missed runs).
  - **DB advisory locks** (e.g. PostgreSQL) to serialize one execution across instances — <https://python.elitedev.in/python/build-distributed-task-scheduler-fastapi-apscheduler/>.
  - *Why it matters here:* the issue's P1-2 chooses **flock leader election among web workers**. That is the *weakest* of these four options — it is the only one that keeps a non-idempotent GitHub-issue-filing + Telegram-sending loop inside a process whose lifecycle is governed by traffic, and it is the option that requires every daemon to be individually converted to be leader-gated. The other three all *remove* the class of problem instead of guarding each instance.
- **Fly.io — the platform this app actually runs on — provides the dedicated-process option natively: `[processes]` groups.** Each named group runs in its own Machine(s) within the app, is scaled independently, and does not compete for resources; the documented example is literally `web = "bin/rails fly:server"` + `cron = "supercronic /app/crontab"`. Source: <https://fly.io/docs/launch/processes/>.
  *Why it matters here:* this is the *platform-canonical* way to run the 5 daemons exactly once (a `cron`/`worker` group), and it is available without a new dependency and without touching the web worker's memory envelope. **Two integration hazards are documented in the same page and are directly relevant:** (a) once a `[processes]` section exists, flyctl treats it as the *complete* list — the existing web group disappears unless added explicitly; (b) services must name the process group (`processes = ["web"]`) and each process that accepts proxy connections must use a **different external port**. The repo's `fly.toml` has a single `[[services]]` with `internal_port = 8000` and no `[processes]` — so this route is a real migration, not a flag.

#### PITFALLS (mandatory)

- **Duplicate side effects from periodic jobs — the most-reported failure.** Long-running cron/beat loops run once per worker; non-idempotent effects (filing an issue, sending a Telegram message) fire N times. Sources: APScheduler #1088; FastAPI discussion #12012 <https://github.com/fastapi/fastapi/discussions/12012>; getorchestra guide — "each process runs its own APScheduler instance by default, causing duplicate periodic jobs" <https://www.getorchestra.io/guides/fastapi-server-workers-a-detailed-guide-with-examples>; a Chinese-language writeup states the same and recommends one worker, file locks, or a shared Redis/DB job store <https://blog.csdn.net/Franciz777/article/details/151935186>.
  *Why it matters here:* `BackupWatcher` files **GitHub issues** and sends **Telegram** — both non-idempotent and externally visible. This is the confirmed problem's P1-2, and it is the field's #1 documented pitfall.
- **Rate-limiter N× drift.** Each worker enforces its own bucket, so the effective ceiling is N× the configured limit, and a client sees *inconsistent* 429s depending on which worker it lands on. Sources: the same multi-worker pitfall class (getorchestra, CSDN above) and the fastapi-practices Redis strategy <https://deepwiki.com/fastapi-practices/fastapi_best_architecture/11.1-redis-caching-strategy>.
  *Why it matters here:* `tortoise/abuse.py` per-IP limiters key on `Fly-Client-IP` (`TORTOISE_TRUST_FLY_CLIENT_IP=1` in `fly.toml`) — so the limit is a *security* control, and N× drift is a fail-open, not a nit.
- **Memory multiplication is not mitigated by `--preload` in this deployment — because uvicorn has no `--preload`.** `--preload`/`preload_app` is a **Gunicorn** feature; grepping `uvicorn/main.py` at `master` for `preload` returns nothing (only `--workers`, and a `--reload`/`--workers` exclusion). The generic production guidance that `--preload` "shares read-only pages via copy-on-write" is Gunicorn/UvicornWorker guidance, not standalone-uvicorn guidance. Sources: render.com FastAPI best practices <https://render.com/articles/fastapi-production-deployment-best-practices>; pythonapibuilders Uvicorn-vs-Gunicorn worker config <https://pythonapibuilders.com/getting-started-with-python-apis-for-builders/setting-up-fastapi/uvicorn-vs-gunicorn-worker-configuration/>; verified absence in <https://github.com/encode/uvicorn/blob/master/uvicorn/main.py>.
  *Why it matters here:* under `spawn`, the ~90MB model + torch + sentence-transformers footprint is **not** shared — it is loaded N times. The only COW route is switching to Gunicorn + `UvicornWorker` + `--preload`, which re-introduces the *opposite* pitfall (below) and is a deployment-architecture change.
- **`--preload`'s own caveats, if that route is ever taken: sockets, DB pools, background threads and event loops opened at import time are inherited by the children and can corrupt behaviour.** Sources: pythonapibuilders — "opening sockets or DB clients at import time can be inherited by child workers and cause corrupted behavior"; edgeservers Gunicorn/Uvicorn tuning — import-time side effects like DB pools and background threads inherited "usually fatally" <https://www.edgeservers.com.au/en/articles/python-gunicorn-uvicorn-tuning>; querystack — sockets and file handles opened at import time are shared across workers and cause subtle bugs <https://www.querystack.tech/post/running-fastapi-in-production-gunicorn-as-process-manager-with-uvicorn-workers-4c4c6b>; toolsguruhub — breaks libraries that initialize connections or event loops at import time <https://www.toolsguruhub.com/blogs/best-gunicorn-worker-types-fastapi>.
  *Why it matters here:* the app's healthz `ThreadingHTTPServer`, its watchdog thread and its `serve_health` listener are all started around lifespan; a preload-based scheme would need every socket/thread created **after** fork or it inherits closed-but-duplicated fds.
- **Fixed-port binds: a second process binding a live port fails with `EADDRINUSE` — `SO_REUSEADDR` does NOT permit it; only `SO_REUSEPORT` does.** The repo's healthz server sets `allow_reuse_address = True` (`monitoring.py::_HealthzServer`), which maps to `SO_REUSEADDR` — sufficient for `TIME_WAIT` reuse, *not* for two live listeners on the same port on Linux.
  *Why it matters here:* **the guard behaves differently than the confirmed problem says** — see *Findings that contradict*, item 3. `start_health_listener()` deliberately swallows the bind failure (`logger.error(...)`; returns `None`) unless `TORTOISE_HEALTHZ_REQUIRED=1`, which is **not set** in `fly.toml [env]`, the Dockerfile or `entrypoint.sh`. So at workers=2 there is no crash: one worker (bind-race winner) serves `/healthz`, and every other worker silently serves nothing on 9090.
- **Connection-pool multiplication against a managed database.** Each worker opens its own pool, so N workers ⇒ N× connections against the managed backend, which has a finite max-client budget; the fix is per-worker pool sizing with an explicitly computed total. Sources: the general multi-worker pitfall class above; the `--preload` sources also note import-time pool creation as the specific hazard.
  *Why it matters here:* prod is FalkorDB Cloud (managed) — an N× connection multiplier is a hard external cap, and it is **not in the confirmed problem's guard inventory**. This is an inventory gap.
- **Observability silently becomes per-worker — a correctness break, not a duplication.** `GoldenSignals`/`collect_signals` compute P99/throughput/error-rate/saturation **in-process**, so at N workers each emits its own four signals and no process holds the app-wide view; a per-worker P99 is not the service's P99.
  *Why it matters here:* this extends the confirmed problem's scope: the incomplete guard set is not only daemons and state holders, it is **also the metrics surface**. A "workers=2 boots and CSRF passes" smoke test would pass while the golden signals quietly went wrong.
- **JWKS/IdP and other library-level in-process single-flight also multiply.** `tortoise/session_auth.py` documents an in-process `{kid: jwk}` cache with "single-flight, cooldown-aware JWKS refetch" — per worker, that is N independent caches, N refetches, and N possibly-desynchronised TTL views of the same IdP metadata.
  *Why it matters here:* another inventory item absent from the confirmed problem; lower severity than CSRF (correctness is preserved, traffic to the IdP is N×), but it belongs in the inventory because the *reason* it is safe-looking ("there's a single-flight lock") is exactly what makes it invisible.

### Axis 2 — Config: the gate surface (medium)

- **Detecting "I am one of N workers" from inside the process — what is and is not available:**
  - **No uvicorn-provided per-worker id exists** (env or argv); `--workers` is a count, and `WEB_CONCURRENCY` is only the *default source* for that count. Source: <https://uvicorn.dev/settings/> + the manpage, and the source read of `_subprocess.py`.
  - **`WEB_CONCURRENCY` is unreliable as an identity signal because CLI wins over env**: uvicorn resolved `workers` from `--workers` if given, else `$WEB_CONCURRENCY`, else 1. So `int(os.environ.get("WEB_CONCURRENCY", 1))` can read 1 while the process is actually worker 3 of 8. Source: <https://uvicorn.dev/settings/>.
  - **`os.getpid()` is process-unique but gives no index and no count.** `multiprocessing.parent_process()` tells you a parent exists but does not identify a uvicorn worker. Search synthesis is explicit that no uvicorn-standard per-worker identity mechanism exists <https://uvicorn.dev/release-notes/>. Note one comparably-deployed project (`Open WebUI`) has an app-specific `INSTANCE_ID` env plus a separate `UVICORN_WORKERS` — i.e. the identity is app-manufactured, not server-provided <https://docs.openwebui.com/reference/env-configuration/>.
  - *Why it matters here:* the reliable formulation is **not** "which worker am I" but "can I acquire the role" — i.e. self-election via `flock_exclusive` (or a bind attempt). That is exactly what the issue's P1-2 proposes and external evidence supports it as the only implementable route.
- **Fail-closed boot validation is a documented, practised pattern:** `pydantic-settings` reads typed config from env and validates it **at startup** so misconfiguration fails before the first request, with `validate_default` / `FailFast` controlling strictness; errors surface as `ValidationError` at boot rather than as a 500 mid-request. Sources: <https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/>; <https://github.com/pydantic/pydantic-settings>; <https://pydantic.dev/articles/pydantic-v2-8-release> (the `FailFast` primitive); practice guide: config errors should happen at startup <https://agentfactory.panaversity.org/docs/Building-Custom-Agents/fastapi-for-agents/environment-variables>.
  *Why it matters here:* the repo has a hand-rolled config surface (`tortoise/config.py` — env precedence for `TORTOISE_DB_URI`/`TORTOISE_DB_PATH`, with explicit `ValueError` raises for relative paths) and **`pydantic-settings` is not installed** (verified: `import pydantic_settings` fails). So a fail-closed worker/embedded-URI assertion is a hand-rolled check today; adopting `pydantic-settings` would be a **new third-party dependency** and is out of scope for this issue (Axis 3).
  - **The availability tradeoff is explicit in the pattern family:** fail-closed at boot converts a configuration error into a crash-loop (loud, deploy-blocking, no partial service) whereas warn-and-continue trades it for a silently degraded process. The repo already carries **both postures side by side** and it is worth naming them: `_healthz_required()` is fail-*open* by default with an opt-in fail-closed flag; `resolve_db_path()` **raises** on a relative path (fail-closed, unconditional). ⚠️ The crash-loop side of the tradeoff was inferred from the uvicorn `STARTUP_FAILURE` source rather than sourced from an availability-patterns document — single-source, verify if this becomes load-bearing.
  - *Why it matters here:* the issue's P1-3 ("entrypoint forces `--workers 1` when the URI is unresolved + app-level assert") has a defensible precedent — it matches the app-level fail-closed style already used in `config.py`. The design question is only whether the assert is fatal (crash-loop) or a logged downgrade; external practice supports **fatal for the embedded-divergence case**, because a divergent embedded DB is silent data corruption, not a degraded feature.

### Axis 3 — Library-deps (trigger assessment only)

- **No new third-party dependency is introduced — justified skip, no queries spent.** The change uses stdlib `fcntl` (already in use), `os`, and the repo's own `tortoise/shared_state/concurrency.py::flock_exclusive`. The one candidate the research surfaced — `pydantic-settings` for typed fail-closed config — is **not indicated**: the repo's existing hand-rolled envelope checks (`tortoise/config.py`) already raise, so the issue needs no new dep. The one *interface* worth flagging is that `tortoise/config.py` is the existing env-precedence surface and any new worker/embedded gate should live beside it rather than in a new module.

## Findings that contradict the confirmed problem

**1. "uvicorn forks with identical env" is wrong — uvicorn `spawn`s. The conclusion survives, the mechanism does not, and the mechanism is what governs the memory analysis.**
The issue body (P1-2) states *"uvicorn forks with identical env, no per-worker id"*. Canonically, uvicorn standalone uses `multiprocessing.get_context("spawn")` (`uvicorn/_subprocess.py`). The **conclusion** the issue draws (no per-worker id ⇒ `TORTOISE_DAEMON_WORKER` is unimplementable) is **still true** — no env or argv identity is passed to the child either way. But the mechanism error matters in three places: (a) under `spawn` each worker **re-imports the app in a fresh interpreter**, so module-level state is re-*executed*, not inherited copy-on-write — which is why the ~85s torch/model pre-warm runs N times in full; (b) the RSS envelope cannot be reasoned about as "1 worker's footprint + COW delta"; (c) any design that relies on import-time state being *shared-but-forked* is inapplicable. Correct the record; do not change the conclusion.

**2. `--preload` is not available in this deployment's process manager, so it is not a mitigation for the memory envelope.**
The brief lists "`--preload` tradeoffs" as a pitfall and Axis 2 asks whether `--preload` changes the per-worker memory envelope. Uvicorn's CLI has **no `--preload` flag** (verified by grepping `uvicorn/main.py` at `master`; `--preload`/`preload_app` is Gunicorn's). Under `spawn` there is no COW sharing at all, so the per-worker memory envelope at workers=2 is **≈ 2× the full import + model footprint**, not "1× + shared pages". The only COW route — Gunicorn + `UvicornWorker` + `--preload` — is a deployment-architecture change that re-introduces the *opposite* documented hazard (import-time sockets/pools/threads inherited across fork are "usually fatal"). **The confirmed problem's guard inventory is therefore missing a guard: the N× model-memory envelope.** "Stagger the pre-warm" (the issue's P1-1 wording) is a *mitigation of the peak*, not a guard, and it does not reduce steady-state RSS. On a 4096MB box this is likely the binding constraint, and the issue's own target (`< ~1.8GB` per worker on a `6144MB+` box) implies a **machine resize**, which is not in the deliverable as stated.

**3. The 9090 listener does not "become per-worker" — it becomes single-worker-but-arbitrary, and the second worker's failure is silently swallowed.**
This is a direct correction of the confirmed problem's characterization. `monitoring.py::start_health_listener` catches `OSError` from the bind and, unless `TORTOISE_HEALTHZ_REQUIRED=1` (**not set** in `fly.toml [env]`, the Dockerfile, or `entrypoint.sh`), logs at ERROR and **returns `None`**. `_HealthzServer` sets `allow_reuse_address = True`, which is `SO_REUSEADDR` and does **not** permit a second live listener on the same port. So at workers=2: the bind-race winner serves `/healthz`, every other worker boots normally with **no** listener, and the only trace is one ERROR line. Consequences the inventory must cover: (i) the "loop is wedged" signal now reports an **arbitrary one** of N loops and is blind to the rest; (ii) `fly.toml` documents this top-level check as **DEPLOY-BLOCKING BY DESIGN** and `deploy-hosted.yml` auto-deploys on `fly.toml` changes — so the swallowed failure is a latent deploy-blocker if the winner ever stops binding, and `TORTOISE_HEALTHZ_REQUIRED` becomes the switch that converts it into a machine-wide crash-loop (see item 4 of Axis 1 canonical: `STARTUP_FAILURE` stops the parent). The correct guard is a **policy decision**, not a code tweak: designate exactly one listener (leader election), move the listener out of the web process, or bind with `SO_REUSEPORT` and *know* that the resulting check is a load-balanced sample of one worker's loop. Note also the recursion this creates with the issue's P1-2: if leader election is implemented for the daemons, the 9090 listener should **share that election** rather than run a second, independent one.

**4. "SIGKILL-safe flock" is true but incomplete — the release-on-fd-close and self-reentrancy caveats are load-bearing for guard work.**
The issue calls `flock_exclusive` "the repo's SIGKILL-safe primitive". That is correct (the kernel releases `flock` on process death, requiring no TTL — which is precisely why it beats a Redis lock here). But two canonical caveats are missing from the inventory: (a) **any file-descriptor close on the same open file description releases the lock** — so if any other code path opens and closes the same lock-file path, the leader silently loses leadership while still believing it holds it; (b) **the same process opening the path twice gets two independent lock descriptions**, so a re-entrant/nested acquire inside one worker does not nest — it raises `BlockingIOError` and surfaces as `TimeoutError` after `timeout_ms`. Guard design implication: the lock file must be a dedicated, never-otherwise-opened path, and the acquire must be provably non-reentrant. (The NFS/CIFS limitation does **not** apply — Fly volumes are host-local block storage.)

**5. The guard inventory is incomplete in two dimensions the confirmed problem does not name: provider/DB connection multiplication, and observability correctness.**
- **FalkorDB Cloud is managed and has a finite client budget.** Each worker opens its own pool ⇒ N× connections. This is an inventory item, an external hard cap, and it is absent from the confirmed problem's list.
- **The four golden signals become per-worker.** `GoldenSignals`/`collect_signals` are in-process, so at N workers the P99/throughput/error-rate/saturation numbers each describe **one worker, not the service** — a correctness break in the observability surface, not merely duplication. A "workers=2 boots, onboarding passes" acceptance test would pass while this silently degrades. Same class, lower severity: `session_auth.py`'s in-process JWKS cache with "single-flight" becomes N caches / N refetches (the in-process lock is exactly what makes it look safe).

**6. The go/no-go trigger's p95 half is not merely unmeasurable — it is unsound as a cause-detector; only the queue-depth half should gate.**
See *Trigger assessment* above. A p95 breach is produced by loop-blocking synchronous DB/LLM work, which the repo documents as present and which raising the worker count does not fix. Restating the gate as queue-depth-primary (post-#1676 offload) with p95 corroborating makes the gate point at the right cause.
